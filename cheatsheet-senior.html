9. SQL

9.17 Isolation Levels Senior

Izolyatsiya darajalari parallel tranzaksiyalar bir-birining o'zgarishlarini qanchalik ko'rishini belgilaydi: READ UNCOMMITTED (dirty read), READ COMMITTED (PostgreSQL default), REPEATABLE READ (MySQL InnoDB default), SERIALIZABLE.

Har bir daraja turli anomaliyalarning oldini oladi: dirty read, non-repeatable read, phantom read, lost update, write skew. Yuqori daraja — ko'proq izolyatsiya, lekin ko'proq lock/serialization xatolari va qayta urinishlar. Implementatsiyalar farq qiladi (InnoDB gap lock'lari, PostgreSQL SSI).

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN;
-- ...
COMMIT;  -- PostgreSQL'da serialization_failure bo'lsa qayta urinish kerak
9.18 Locks va Deadlocks Senior

Lock'lar parallel o'zgarishlarni tartibga soladi: row-level (SELECT ... FOR UPDATE — eksklyuziv, FOR SHARE — umumiy), table-level, InnoDB'da gap/next-key lock'lar. SKIP LOCKED (navbat jadvallari uchun), NOWAIT.

Deadlock — ikki tranzaksiya bir-birining lock'ini kutadi; DB birini qurbon qilib rollback qiladi. Oldini olish: resurslarni har doim bir xil tartibda lock qilish, tranzaksiyani qisqa saqlash, kerakli indekslar (indekssiz UPDATE ko'p qatorni lock qiladi), qayta urinish logikasi.

// Doim kichik id birinchi — deadlock'ning oldini oladi
[$a, $b] = $from->id < $to->id ? [$from, $to] : [$to, $from];
Account::whereKey([$a->id, $b->id])->orderBy('id')->lockForUpdate()->get();

10. MySQL

10.10 Transactions va Isolation Levels Senior

InnoDB default izolyatsiyasi — REPEATABLE READ: tranzaksiya ichidagi oddiy SELECT lar bir xil snapshot'ni ko'radi; locking o'qishlar (FOR UPDATE, UPDATE) esa eng so'nggi commit qilingan ma'lumot bilan ishlaydi va next-key lock'lar orqali phantom'larni oldini oladi.

Ko'p yuqori yuklamali tizimlar READ COMMITTED ga o'tadi — kamroq gap lock, kamroq deadlock. autocommit=1 default; Laravel DB::transaction START TRANSACTION/COMMIT ni boshqaradi. DDL implicit commit qiladi.

SELECT @@transaction_isolation;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
10.11 Row-level Locking Senior

InnoDB lock turlari: record lock (indeks yozuvi), gap lock (yozuvlar orasidagi bo'shliq — phantom'larga qarshi), next-key lock (record + gap), insert intention lock. Shared (S) va exclusive (X) rejimlar, jadval darajasida intention lock'lar (IS/IX).

Muhim: lock'lar indeks yozuvlariga qo'yiladi — WHERE sharti indeksdan foydalanmasa, InnoDB ko'p (hatto barcha) qatorlarni lock qiladi. performance_schema.data_locks va sys.innodb_lock_waits lock kutishlarini ko'rsatadi.

SELECT * FROM performance_schema.data_locks\G
SELECT * FROM sys.innodb_lock_waits\G
10.12 Deadlocks Senior

InnoDB deadlock'ni darhol aniqlaydi (wait-for graph) va "arzonroq" tranzaksiyani rollback qiladi (xato 1213). SHOW ENGINE INNODB STATUS ning LATEST DETECTED DEADLOCK bo'limi oxirgi deadlock'ni ko'rsatadi; innodb_print_all_deadlocks=ON hammasini log'ga yozadi.

Kamaytirish: bir xil tartibda lock olish, qisqa tranzaksiyalar, to'g'ri indekslar (kamroq qator lock'lanadi), READ COMMITTED (gap lock kamroq), katta batch'larni bo'lish. Deadlock'ni butunlay yo'qotib bo'lmaydi — ilova qayta urinishga tayyor bo'lishi kerak (DB::transaction(..., attempts: 3)).

SET GLOBAL innodb_print_all_deadlocks = ON;
SHOW ENGINE INNODB STATUS\G

11. PostgreSQL

11.10 MVCC Senior

PostgreSQL MVCC'da UPDATE qatorni joyida o'zgartirmaydi: yangi versiya (tuple) yoziladi, eskisi "o'lik" bo'lib qoladi. Har bir tuple'da xmin/xmax tranzaksiya id'lari; snapshot qaysi versiya ko'rinishini belgilaydi.

Oqibatlar: o'lik tuple'lar jadval va indekslarni shishiradi (bloat) — VACUUM tozalaydi; uzoq ochiq tranzaksiya VACUUM'ni bloklaydi; ko'p UPDATE li jadvallarda fillfactor va HOT update'lar muhim. Transaction ID wraparound — VACUUM ishlamasa DB himoya uchun yozishni to'xtatadi.

SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
11.11 Transactions va Isolation Levels Senior

PostgreSQL default — READ COMMITTED: har bir buyruq yangi snapshot oladi. REPEATABLE READ — tranzaksiya boshidagi snapshot (phantom'larsiz), parallel o'zgarishda could not serialize access xatosi. SERIALIZABLE — SSI (Serializable Snapshot Isolation): to'liq izolyatsiya, serializatsiya xatolarida qayta urinish shart. READ UNCOMMITTED amalda READ COMMITTED kabi ishlaydi.

DDL tranzaksiyaviy — migratsiya muvaffaqiyatsiz bo'lsa to'liq rollback (MySQL'dan katta afzallik). Savepoint'lar: Laravel ichma-ich DB::transaction ularni avtomatik ishlatadi.

BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ...
COMMIT;  -- SQLSTATE 40001 bo'lsa, butun tranzaksiyani qayta urinish
11.12 Locks va Deadlocks Senior

Qator lock'lari: FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE, FOR KEY SHARE; NOWAIT, SKIP LOCKED (navbat jadvallari — Laravel database queue ham ishlatadi). Jadval lock'lari 8 rejimda; DDL ko'pincha ACCESS EXCLUSIVE oladi — katta jadvalda ALTER TABLE barcha so'rovlarni to'xtatib qo'yishi mumkin.

Xavfsiz migratsiya: lock_timeout o'rnatish, indeksni CREATE INDEX CONCURRENTLY, NOT NULL ni CHECK ... NOT VALID + VALIDATE orqali. Deadlock'ni PostgreSQL deadlock_timeout dan keyin aniqlaydi va bir tranzaksiyani bekor qiladi; pg_locks + pg_blocking_pids() tahlil uchun.

SET lock_timeout = '3s';
CREATE INDEX CONCURRENTLY orders_status ON orders (status);
SELECT pid, pg_blocking_pids(pid), query FROM pg_stat_activity WHERE wait_event_type = 'Lock';
11.23 Connection Pooling Senior

Har PostgreSQL ulanishi alohida process (bir necha MB xotira) — yuzlab ulanish serverni bo'g'adi. Ko'p FPM worker'li Laravel ilovalari uchun PgBouncer odatiy: transaction pooling rejimida bir nechta server ulanishi minglab mijozga xizmat qiladi.

Transaction pooling cheklovlari: sessiya holati (SET, advisory lock'lar sessiya darajasida, LISTEN) ishlamaydi; prepared statement'lar PgBouncer 1.21+ da qo'llab-quvvatlanadi. Laravel'da odatda emulated prepares yoki to'g'ri sozlangan PgBouncer bilan muammosiz ishlaydi.

17. Database Transactions

17.5 Isolation Levels Senior

To'rt standart daraja va ular oldini oladigan anomaliyalar:

| Daraja | Dirty read | Non-repeatable | Phantom |

|---|---|---|---|

| READ UNCOMMITTED | ✗ | ✗ | ✗ |

| READ COMMITTED | ✓ | ✗ | ✗ |

| REPEATABLE READ | ✓ | ✓ | ✗ (InnoDB/PG'da amalda ✓) |

| SERIALIZABLE | ✓ | ✓ | ✓ |

Lost update va write skew alohida ko'rib chiqiladi. Yuqori daraja — kamroq anomaliya, lekin ko'proq lock yoki serializatsiya xatosi. Odatiy yondashuv: default daraja + kerakli joyda aniq lock (FOR UPDATE) yoki atomik so'rov.

DB::statement('SET TRANSACTION ISOLATION LEVEL SERIALIZABLE');
DB::transaction(fn () => /* ... */, attempts: 5);
17.9 Lost Updates Senior

Lost update — ikki tranzaksiya bir qiymatni o'qiydi, har biri o'zgartirib yozadi, va birining o'zgarishi ikkinchisi tomonidan qayta yoziladi. Klassik misol: zaxira qty = 10, ikki so'rov o'qiydi, har biri qty = 9 yozadi — natija 9, aslida 8 bo'lishi kerak edi.

Yechimlar: atomik so'rov (UPDATE ... SET qty = qty - 1 WHERE qty > 0), pessimistic lock (lockForUpdate()), optimistic lock (version ustuni), SERIALIZABLE (PostgreSQL buni xato sifatida aniqlaydi). Eloquent'da $model->qty--; $model->save() lost update'ga moyil.

// ❌ lost update
$p = Product::find($id); $p->stock -= 1; $p->save();
// ✅ atomik
$ok = Product::whereKey($id)->where('stock', '>', 0)->decrement('stock');
17.10 Pessimistic Locking Senior

Pessimistic locking — ziddiyat bo'ladi deb hisoblab, qatorni oldindan qulflash: SELECT ... FOR UPDATE (boshqalar yozolmaydi va FOR UPDATE bilan o'qiyolmaydi), FOR SHARE (boshqalar o'qiydi, yozolmaydi). Lock tranzaksiya oxirigacha saqlanadi.

Laravel: ->lockForUpdate(), ->sharedLock(). Qoidalar: faqat tranzaksiya ichida; lock'ni imkon qadar kech olib, tez bo'shatish; deadlock'ning oldini olish uchun barqaror tartib; NOWAIT/SKIP LOCKED kutishni boshqarish uchun. Ziddiyat ko'p va konflikt narxi yuqori bo'lgan joylar uchun (moliya).

DB::transaction(function () use ($accountId, $amount) {
    $account = Account::whereKey($accountId)->lockForUpdate()->firstOrFail();
    if ($account->balance < $amount) {
        throw new InsufficientFunds();
    }
    $account->decrement('balance', $amount);
});
17.11 Optimistic Locking Senior

Optimistic locking — ziddiyat kam deb hisoblab, qulflamasdan ishlash va yozishda tekshirish: version (yoki updated_at) ustuni; UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?; o'zgargan qatorlar soni 0 bo'lsa — konflikt.

Afzalliklari: lock yo'q, uzoq "o'qish-tahrir-saqlash" jarayonlari (forma ochiq turadi) uchun mos, yuqori parallellik. Konfliktda: foydalanuvchiga "ma'lumot o'zgargan, qayta yuklang" yoki avtomatik qayta urinish. API'da ETag/If-Match header bilan birgalikda.

$affected = Document::whereKey($doc->id)
    ->where('version', $request->integer('version'))
    ->update([...$data, 'version' => DB::raw('version + 1')]);

abort_if($affected === 0, 409, 'Hujjat boshqa foydalanuvchi tomonidan o\'zgartirilgan');
17.16 External API Calls inside Transactions Senior

Tranzaksiya ichida tashqi HTTP chaqiruv — klassik xato: (1) tarmoq sekin bo'lsa tranzaksiya va lock'lar uzoq ushlanadi; (2) API muvaffaqiyatli, keyin DB rollback — tashqi tizimda amal bajarilgan, bizda yozuv yo'q (masalan, pul yechilgan, buyurtma yo'q); (3) aksincha ham bo'lishi mumkin.

To'g'ri yondashuvlar: avval lokal yozuvni "pending" holatda commit qilish → tashqi chaqiruv → natijani alohida tranzaksiyada saqlash; idempotency key bilan qayta urinish; outbox pattern; kompensatsiya amallari (refund). Holat mashinasi barcha oraliq holatlarni aniq qiladi.

$payment = Payment::create(['order_id' => $order->id, 'status' => 'pending', 'idempotency_key' => Str::uuid()]);
$result = $gateway->charge($order->total, idempotencyKey: $payment->idempotency_key); // tranzaksiyadan tashqarida
DB::transaction(fn () => $payment->markAs($result->status));

21. OAuth 2.0

21.3 PKCE Senior

PKCE (Proof Key for Code Exchange, RFC 7636) — authorization code'ni ushlab qolish hujumidan himoya. Client tasodifiy code_verifier yaratadi, uning SHA-256 hash'ini (code_challenge) /authorize ga yuboradi; /token da asl code_verifier ni ko'rsatadi. Dastlab public client'lar (mobil, SPA) uchun yaratilgan, endi barcha client'lar uchun majburiy tavsiya (OAuth 2.1). Faqat S256 metodi (plain — yo'q).

$verifier  = Str::random(64);
$challenge = rtrim(strtr(base64_encode(hash('sha256', $verifier, true)), '+/', '-_'), '=');
session(['pkce_verifier' => $verifier]);

22. JWT

22.5 Signing Algorithms Senior

Simmetrik (HS256/384/512 — HMAC): bitta maxfiy kalit imzolaydi va tekshiradi — barcha tekshiruvchilar imzolay ham oladi; faqat bitta servis ichida. 22.14 Algorithm Confusion Risks Senior

85.6 Security Assessment Senior

Xavfsizlik chegaralari (Trust Boundaries) qayerda? Autentifikatsiya qanday uzatiladi? Nozik ma'lumotlar (parollar, kartalar) qayerda va qanday shifrlanadi? Ichki tarmoqda 'Zero Trust' tamoyili bormi yoki faqat tashqi perimetr himoyalanganmi? Arxitektura darajasidagi xavfsizlik bo'shlig'ini keyinchalik kod bilan yopib bo'lmaydi.

85.7 Performance Assessment Senior

Unumdorlikni oldindan baholash — taklif qilinayotgan arxitektura kerakli javob vaqtini (masalan p95 < 100 ms) bera oladimi?

So'rov yo'lida qancha tarmoq sakrashlari (network hops) bor? Bitta foydalanuvchi so'rovi ketidan 10 ta ichki servisga sinxron so'rov ketmayaptimi (Distributed N+1)? Kesh qayerda turibdi va kesh bo'lmaganda (cache miss) baza yuklamani ko'tara oladimi? Hisob-kitoblar bilan unumdorlik isbotlanishi kerak.

85.8 Scalability Assessment Senior

Masshtablanuvchanlik auditi — tizim 10 barobar yuklama kelganda shunchaki yangi server qo'shish bilan (gorizontal) kengaya oladimi?

Arxitekturada 'yagona bo'yinbog'lar' (Bottlenecks) bormi? Masalan: barcha yozishlar bitta MySQL masterga borishi yoki xotirada holat saqlovchi (stateful) komponentlar mavjudligi. Stateless veb-qatlam, ma'lumotlar bazasi replikalari va asinxron navbatlar orqali gorizontal kengayish imkoniyati tekshiriladi.

85.9 Availability and Resilience Senior

Mavjudlik va chidamlilik — tizimning 99.9% yoki 99.99% ishlash kafolati (SLA).

Single Point of Failure (SPOF) bormi? Bitta server, bitta ma'lumotlar bazasi yoki bitta Availability Zone o'chib qolsa nima bo'ladi? Multi-AZ, avtomatik failover, yuklama taqsimlagichlar (ALB) va sog'lomlik tekshiruvlari (Health Checks) mavjudligi tekshiriladi.

85.10 Failure Modes Senior

Nosozlik rejimlari va kaskadli to'xtashlar tahlili — 'Agar komponent X ishlamay qolsa, nima bo'ladi?'.

Agar Redis o'chsa, butun sayt yiqiladimi yoki shunchaki sekinlashib ishlayveradimi (Graceful Degradation)? Agar to'lov tizimi javob bermasa, buyurtmalar navbatda kutadimi yoki xatolik bilan bekor bo'ladimi? Circuit Breaker, Timeout, Retry va Dead Letter Queue mexanizmlari tekshiriladi.

85.13 Migration Strategy Lead

Eski tizimdan yangisiga o'tish strategiyasi — yangi arxitekturaga qanday qilib ishlab turgan foydalanuvchilarni to'xtatmasdan o'tiladi.

Strangler Fig naqshi: yangi tizim eski tizim atrofida quriladi va trafik asta-sekin (1%, 5%, 50%, 100%) yangi tizimga yo'naltiriladi (Canary Release). Ma'lumotlar bazasini parallel yozish (Dual-writing) va uzilishsiz orqaga qaytish (Rollback) rejasi tekshiriladi.

85.14 Backward Compatibility Senior

Yangi arxitekturaning mavjud tizimlar bilan mosligi.

Eski mobil ilovalar, uchinchi tomon integratsiyalari va mavjud bazalar yangi arxitektura sababli buzilmasligini tekshirish. Agar arxitektura mavjud ma'lumotlar strukturasini o'zgartirsa, eski mijozlarni qo'llab-quvvatlash uchun adapter qatlami (Anti-Corruption Layer) mavjudligi nazorat qilinadi.

85.16 Operational Complexity Lead

Operatsion murakkablik — ishlab chiqarishdagi tizimni saqlash, boshqarish va xatolarni tuzatish jamoaga qanchalik og'ir bo'ladi.

Agar 3 kishilik kichik jamoa 15 ta mikroservis, Kafka, Kubernetes va 4 xil ma'lumotlar bazasidan iborat arxitekturani tanlagan bo'lsa — ular kod yozish o'rniga faqat infratuzilmani tuzatish bilan ovora bo'ladi. Arxitektura jamoaning o'lchami va tajribasiga mutanosib bo'lishi shart.

85.17 ADR Review Senior

Arxitektura qarorlari jurnallarini (ADR) ko'rib chiqish va tasdiqlash.

Yangi arxitekturaviy taklif bilan birga uning sabablari va muqobillari keltirilgan ADR taqdim etilganmi? Barcha jamoa yetakchilari va arxitektorlar ushbu ADR ni o'qib, o'z e'tirozlarini bildiradilar va yakunda 'Accepted' yoki 'Rejected' statusi qo'yiladi.

85.19 Risks and Mitigations Senior

Xatarlar va ularni yumshatish choralari xaritasi — arxitektura tahlilining yakuniy xavfsizlik to'ri.

Aniqlangan har bir arxitekturaviy xavf (masalan: tashqi servisning sekin javob berishi) yoniga uni bartaraf etuvchi aniq muhandislik yechimi (masalan: 2 soniyalik timeout, Redis kesh fallback va asinxron navbat) yoziladi. Xatarlari yechilmagan loyiha kodlashga o'tishiga ruxsat berilmaydi.

85.20 Architecture Evolution Lead

Evolyutsion arxitektura — arxitekturani toshga o'yib yozilgan qotib qolgan narsa emas, balki biznes va yuklama o'sishi bilan doimiy o'zgarib boruvchi tirik organizm sifatida loyihalash.

Loyiha bugungi talabga mos kelishi kerak, lekin 2 yildan keyin uni o'zgartirishni butunlay imkonsiz qilib qo'ymasligi lozim. Modullararo chegaralar va toza interfeyslar kelajakda butun boshli komponentlarni boshqa texnologiyalarga oson almashtirish imkonini beradi.

80.3 Architecture Documentation Senior

81. Problem Solving

81.4 Root Cause Analysis Senior

Tub sababni tahlil qilish (Root Cause Analysis - RCA) — muammoning yuzaki oqibatini emas, unga sabab bo'lgan asosiy omilni aniqlash.

'5 Nega' (5 Whys) usuli qo'llaniladi: 'Server to'xtadi. Nega? Xotira to'ldi. Nega? Workerlar qayta ishga tushmadi. Nega? Log fayl kattalashib ketdi...'. Natijada shunchaki serverni qayta yuklash (yuzaki yechim) emas, balki log aylantirish va xotira limiti (tub sabab) to'g'rilanadi.

81.9 Trade-off Evaluation Senior

Murosalar tahlili (Trade-offs) — dasturiy muhandislikda mukammal yechim yo'qligini, har bir tanlovning o'z narxi va yutuqlari borligini anglash.

Tezlik vs Xotira sarfi; Qulaylik vs Xavfsizlik; Kuchli izchillik (Strong Consistency) vs Yuqori mavjudlik (High Availability); Tayyor kutubxona ishlatish vs O'zimiz yozishimiz. Senior dasturchi biznes vaziyatiga qarab eng to'g'ri murosani asoslab beradi.

81.10 Risk Identification Senior

Xatarlarni oldindan aniqlash — taklif qilinayotgan yechim tizimning boshqa qismlariga qanday kutilmagan zarar yetkazishi mumkinligini baholash.

'Bu yangi indeks yozish tezligini sekinlashtirmaydimi?', 'Bu kesh tozalanishi kesh stampede (kesh lavinasi) keltirib chiqarmaydimi?', 'Tashqi API to'xtab qolsa bizning navbatlar tiqilib qolmaydimi?'. Xatarlarni oldindan ko'rib, himoya choralarini (Circuit Breaker, Rate Limit, Fallback) kiritish.

81.16 Communicating Findings Senior

Xulosalarni to'g'ri yetkazish — topilgan muammo va yechimni turli auditoriyaga (rahbariyat, mijozlar, jamoa) mos tilda tushuntira olish.

Boshqaruvga: biznesga ta'siri, moliyaviy yo'qotish va ko'rilgan choralar qisqa aytiladi; Jamoaga: texnik sabablar, koddagi xato, arxitekturaviy saboqlar batafsil yoritiladi. Shaffof va xotirjam muloqot ishonchni mustahkamlaydi.

82. Technical Decision-Making

82.3 Build vs Buy Senior

O'zimiz yozamiz yoki tayyorini sotib olamiz (Build vs Buy) — asosiy raqobat ustunligini belgilovchi qaror.

Kompaniyaning asosiy qiymati (Core Domain) bo'lmagan narsalarni (masalan: autentifikatsiya uchun Auth0, to'lov uchun Stripe, loglar uchun Datadog, transactional email uchun Postmark) o'zimiz noldan yozishimiz kerak emas. Biznesingiz nimada pul ishlasa, o'shani o'zingiz yozasiz; qolgan hamma narsani tayyori sotib olinadi yoki ochiq kodli kutubxona ishlatiladi.

82.4 Trade-off Analysis Senior

Murosalar tahlili — hech bir texnologiya bepul mo'jiza keltirmasligini bilish.

Har bir texnik qaror nimadir beradi va evaziga nimadir oladi. Masalan: Mikroxizmatlarga o'tish mustaqillik beradi, lekin tarmoq kechikishi va operatsion murakkablikni 10 barobarga oshiradi. Senior dasturchi 'Qaysi muammoni sotib olyapmiz?' savoliga aniq javob beradi.

82.8 Security Implications Senior

Xavfsizlik oqibatlarini tahlil qilish — har qanday yangi arxitektura yoki kutubxona xavfsizlik darajasini qanday o'zgartiradi.

Uchinchi tomon servisini ulash yangi hujum yuzasini (attack surface) ochadi. Yangi kutubxona o'rnatilganda supply chain zaifliklari paydo bo'lmaydimi? Ma'lumotlar saqlanishi va tranziti shifrlanganmi? Barcha qarorlar xavfsizlik prizmasidan o'tkaziladi.

82.10 Backward Compatibility Senior

Orqaga moslikni saqlash talabi — yangi texnologik qaror mavjud mijozlar va tizimlarni buzmasligi lozim.

Agar yangi arxitekturaga o'tish eski mobil ilovalarni ishlamay qolishiga olib kelsa — biznes millionlab dollarlik mijozlarini yo'qotadi. Qaror doim orqaga moslikni va bosqichma-bosqich migratsiya qilish yo'lini ta'minlashi shart.

82.11 Evidence-Based Decisions Senior

Dalillarga asoslangan qarorlar — 'Menga bu texnologiya yoqadi' degan shaxsiy xohish o'rniga, benchmarking, prototip (POC) va aniq raqamlarga tayanish.

Proof of Concept (POC) yaratiladi: 2 ta kutubxona haqiqiy yuklamada sinovdan o'tkaziladi, xotira sarfi va tezligi o'lchanadi. Qaror hisobotida jamoa ko'rishi uchun ushbu test natijalari ilova qilinadi.

82.12 Architecture Decision Records Senior

Qarorlarni ADR formatida muhrlash — qabul qilingan texnik qarorlarni nima sababdan tanlanganini hujjatlashtirish.

Kelajakda (1-2 yildan so'ng) yangi jamoa a'zolari: 'Nega bular bunday g'alati yechim qilishgan?' deb hayron bo'lmasligi uchun ADR kontekst va o'sha paytdagi cheklovlarni tushuntirib beradi. ADR bo'lmasa, jamoa eski xatolarni qayta-qayta takrorlaydi.

84. Technical Leadership

84.1 Technical Direction Lead

Texnik qarash va yo'nalish (Technical Vision) — loyihaning texnologik kelajagini 1-2 yil oldinga ko'ra bilish.

Biz qaysi tomonga ketyapmiz? Qaysi eskirgan texnologiyalardan bosqichma-bosqich voz kechamiz? Yangi PHP/Laravel versiyalari, asinxron arxitektura va bulut servislariga qachon o'tamiz? Tech Lead jamoaga shunchaki 'bugungi topshiriq'ni emas, uzoq muddatli texnik strategiyani ko'rsatib beradi.

84.2 Architecture Ownership Lead

Arxitektura egaligi — butun tizim arxitekturasining yaxlitligi, mustahkamligi va tozaligi uchun bosh mas'ul bo'lish.

Bu degani hamma arxitekturani bitta odam o'zi chizadi degani emas. Tech Lead butun jamoaning arxitekturaviy takliflarini muhokama qiladi, ularni tekshiradi, lekin yakuniy texnik yaxlitlik uchun shaxsiy javobgarlikni o'z zimmasiga oladi.

84.3 Technical Standards Senior

Texnik standartlarni o'rnatish — kod bazasining bir xil, sifatli va bashorat qilinadigan bo'lishini ta'minlovchi qonun-qoidalar.

PSR-12 uslubi, Laravel Pint, PHPStan 8-daraja, Git branch nomlash standartlari, commit qoidalari (Conventional Commits), API javoblarining yagona formati. Standartlar shaxsiy fikr bilan emas, avtomatlashtirilgan CI linterlar orqali tekshirilishi kerak.

84.4 Engineering Best Practices Senior

Muhandislikning ilg'or amaliyotlarini joriy qilish — TDD, CI/CD, avtomatlashtirilgan testlash, xavfsiz migratsiyalar va monitoring madaniyatini yoyish.

Yetakchi dasturchi nafaqat o'zi eng yaxshi amaliyotlarga rioya qiladi, balki jamoada ham 'test yozmasdan turib kod deploy qilinmasligi' yoki 'loglarsiz funksiya qabul qilinmasligi' kabi sog'lom muhandislik immunitetini hosil qiladi.

84.6 Prioritization Senior

Texnik vazifalarni ustuvorlashtirish — biznes vazifalari va texnik qarzlar o'rtasida muvozanatli balansni ta'minlash.

Sprint vaqtining 70-80% i biznes xususiyatlariga (features), 20% i esa doimiy texnik qarzni to'lash, xatolarni tuzatish va kutubxonalarni yangilashga ajratilishini (20% Tech Time qoidasi) ta'minlash va buni biznesga himoya qilib berish.

84.8 Mentoring Senior

Yetakchining murabbiylik roli — jamoa a'zolarini professional rivojlantirish va ularni yangi darajaga olib chiqish.

Tech Lead o'zidan keyin yangi liderlarni tarbiyalaydi. U bilimlarni yashirmaydi, aksincha o'z o'rnini bosa oladigan kuchli muhandislarni yetishtirib, jamoaning texnik mustaqilligini oshiradi.

84.10 Risk Management Senior

Loyihaviy va texnik xatarlarni tizimli boshqarish — nimalar noto'g'ri ketishi mumkinligini oldindan ko'rish va ehtiyot choralarini ko'rish.

Xatarlar ro'yxati (Risk Register) yuritiladi: uchinchi tomon API lari ishlamay qolishi, server quvvati yetmay qolishi, asosiy kadrning ketib qolishi. Har bir xavf uchun uning ehtimoli, zarari va oldini olish choralari rejalashtiriladi.

84.11 Incident Leadership Lead

Favqulodda hodisalarni boshqarish (Incident Commander) — ishlab chiqarish tizimi yiqilganda (Production Outage) boshqaruvni qo'lga olish.

Vahimani to'xtatish, yagona aloqa kanalini (Incident Room) ochish, vazifalarni aniq taqsimlash (kim logni qaraydi, kim bazani tekshiradi, kim rahbariyatga xabar beradi), tezkor tiklash (Rollback / Failover) va hodisadan keyin Blameless Post-Mortem o'tkazish.

84.12 Technical Debt Management Senior

Texnik qarzni strategik boshqarish — texnik qarzning kritik massaga aylanib, loyiha rivojini to'xtatib qo'yishining oldini olish.

Koddagi texnik qarzlar inventarizatsiyasi yuritiladi, ularning biznesga zarari baholanadi va har bir sprintda muntazam ravishda eng og'ir qismlar refactoring qilinadi.

84.13 Stakeholder Communication Lead

Rahbariyat va biznes egalari bilan muloqot — texnik muammolarni biznes tushunadigan tilda (foyda, yo'qotish, tezlik, risk) taqdim etish.

Rahbariyatga 'Biz N+1 so'rovlarni hal qilishimiz kerak' deyish samarasiz; 'Biz bazani optimallashtirsak, server narxi oyiga $400 ga kamayadi va sahifa ochilishi 2 barobarga tezlashadi' deyish kerak. Bu ishonchni oshiradi va byudjet ajratilishini osonlashtiradi.

84.14 Delivery Quality Senior

Yetkazib berish sifati va barqarorligi — tezlik deb sifatni qurbon qilmaslik tamoyili.

Ko'pincha biznes tezroq chiqarishni talab qiladi. Yetakchi muhandis sifat darvozasini (Quality Gates) himoya qiladi: 'Ha, biz tez bajaramiz, lekin testlar va xavfsizlik tekshiruvlarisiz productionga chiqmaymiz'. Shoshma-shosharlik bilan chiqarilgan chala kod keyinroq 5 barobar ko'p vaqtni yutib ketadi.

84.18 Business and Technical Alignment Lead

Biznes va texnika manfaatlari mushtarakligi — dasturiy ta'minot mustaqil san'at asari emas, biznesga xizmat qiluvchi asbob ekanligini anglash.

Senior muhandis biznes modelni, kompaniya qanday pul ishlayotganini, raqobatchilarni va mijozlar talablarini tushunadi. Texnik qarorlar har doim kompaniyaning strategik maqsadlariga mos kelishi shart.
